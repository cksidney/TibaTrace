# DawaTrace API Architecture

## Route Groups

- `/api/platform/`, `/api/identity/`
- `/api/organizations/`, `/api/patients/`, `/api/practitioners/`
- `/api/prescriptions/`, `/api/dispensing/`
- `/api/clinical/`, `/api/cds/`, `/api/terminology/`
- `/api/fhir/r4/`, `/api/audit/`, `/api/documents/`
- `/api/health/`, `/api/schema/`, `/api/docs/`

OpenAPI is generated by drf-spectacular for the domain API. FHIR is excluded from
OpenAPI because the R4 `CapabilityStatement` at `/api/fhir/r4/metadata` is its
authoritative machine contract.

## Request Controls

Authenticated API requests carry an `X-Tenant-ID` or use the authenticated local
tenant. Non-platform identities cannot switch tenant. Viewsets filter with an
explicit tenant before object lookup. Capabilities distinguish read, write,
review, approve, dispense, override, terminology, audit, and document actions.

Errors use stable DRF responses at domain routes and FHIR `OperationOutcome` at
the FHIR boundary. Correlation IDs are accepted/generated and returned in
`X-Request-ID`. Idempotency keys are tenant-qualified for FHIR writes, dispensing,
notifications, and provider outboxes.

## Write Boundaries

Clinical writes must use `ClinicalDomainService`; prescription state changes use
`PrescriptionWorkflowService`; dispensing uses `DispensingEngine`; CDS uses
`ClinicalDecisionSupportService`. Serializer persistence cannot bypass these
stateful operations.
